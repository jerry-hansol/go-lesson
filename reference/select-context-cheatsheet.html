select·context 치트시트

다중 채널 대기와 취소 전파. 출처: Go by Example, Go Concurrency Patterns: Context.

select 패턴 3종

// ① 타임아웃 — 늦으면 포기
select {
case v := <-ch:
    use(v)
case <-time.After(100 * time.Millisecond):
    // 시한 초과 처리
}

// ② 논블로킹 — 있으면 받고 없으면 지나감
select {
case v := <-ch:
    use(v)
default:
    // 지금은 없음
}

// ③ 취소 대응 워커 — 일 vs 중단 신호
select {
case <-time.After(cost):        // 또는 case out <- result:
    // 작업 진행
case <-ctx.Done():
    return                       // ctx.Err()에 사유
}
  • 여러 case 동시 준비 → 무작위 하나 실행 (기아 방지). 순서 의존 금지.
  • case 없는 select {}는 영원히 블록.

context 생성 계보

생성용도
context.Background()루트. main·서버 시작점에서만
context.WithCancel(parent)수동 취소 — cancel() 호출 시
context.WithTimeout(parent, d)시한부 — d 경과 시 자동 취소
context.WithDeadline(parent, t)절대 시각 기준 시한부
context.WithValue(parent, k, v)요청 스코프 값 (요청 ID 등) — 남용 금지

규칙 (실무 관례)

  • 함수 첫 인자로 받고, 아래로 계속 넘긴다: func f(ctx context.Context, ...)
  • cancel을 받았으면 defer cancel() — 안 하면 go vet의 lostcancel이 context leak으로 잡는다
  • ctx.Done()은 select의 case로. ctx.Err()는 context.Canceled(수동/클라이언트 이탈) vs context.DeadlineExceeded(시한 초과)
  • 부모 취소 → 자손 전부 취소. HTTP 핸들러에서는 r.Context()가 출발점 (클라이언트가 끊으면 취소됨)
  • struct 필드에 저장하지 말고 호출마다 인자로 전달 (공식 블로그 권고)

함정 표

함정증상처방
cancel 버리기 (ctx, _ :=)vet: "should be called, not discarded" — 타이머 누수defer cancel()
닫힌 채널을 select에서 계속 수신해당 case가 항상 즉시 준비 → CPU 100% 무한 루프v, ok := <-ch로 받고 !ok면 ch = nil — nil 채널은 select에서 영원히 준비 안 됨
루프 안에서 매번 time.After반복마다 새 타이머 할당 — 낭비time.NewTimer 재사용 (심화)
select 순서에 의존간헐적 버그 (동시 준비 시 무작위)우선순위가 필요하면 select 중첩으로 명시
