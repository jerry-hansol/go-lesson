Lesson 0015 · Pion·WebRTC

WebRTC 큰 그림 — 시그널링 없이 두 피어 연결하기

Pion·WebRTC 아크 개막. 회사에서 매일 마주치는 pion이 정확히 무엇을 구현한 것인지 — WebRTC의 뼈대(시그널링·SDP·상태 머신)를 알고, 두 피어를 내 맥에서 직접 연결한다. 예상 소요: 40–45분.

오늘의 목표 (하나만)

시그널링 서버 없이(SDP를 변수로 전달) 한 프로세스 안에서 두 WebRTC 피어를 연결하고, offer/answer 모델과 PeerConnection 상태 머신을 설명할 수 있다.

1. WebRTC와 pion — 무엇이고 왜

WebRTC는 브라우저 간 실시간 P2P 통신(음성·영상·데이터)의 IETF/W3C 표준이다. 미디어 협상(SDP), 연결 수립(ICE), 보안(DTLS/SRTP)까지 정해놓고, 딱 하나를 표준 밖에 남겼다 — 시그널링, 즉 "그 SDP를 상대에게 어떻게 전달하느냐". HTTP든 WebSocket이든 쪽지든 애플리케이션 마음이다 (WebRTC for the Curious — Signaling).

pion/webrtc는 이 표준의 순수 Go 구현이다. 브라우저 밖 — 서버, CLI, 임베디드 — 에서 WebRTC를 말할 수 있게 해주며, 레슨 0014에서 본 mediamtx의 WebRTC 서버도, LiveKit SFU도 pion 위에 서 있다. 회사 Go 프로젝트에서 pion을 계속 만나는 이유다.

브라우저 API (JS)pion (Go)
new RTCPeerConnection()webrtc.NewPeerConnection(webrtc.Configuration{})
pc.createOffer() (Promise)pc.CreateOffer(nil) — (값, error) 관례 (레슨 0003)
pc.ondatachannel = ...pc.OnDataChannel(func(...){...}) — 콜백 등록 함수

API가 브라우저와 거의 1:1이라, pion을 익히면 브라우저 쪽 코드도 읽힌다.

2. SDP와 offer/answer 모델

연결하려는 두 피어는 "나는 이런 통신을 할 수 있다"라는 자기소개서 — SDP — 를 교환한다. 한쪽이 제안(offer)하고 상대가 응답(answer)하는 offer/answer 모델이며, 각 피어는 자기 것을 SetLocalDescription, 상대 것을 SetRemoteDescription으로 등록한다 — 총 4개의 설정 호출:

순서피어호출
①pc1CreateOffer → SetLocalDescription(offer)
②pc2SetRemoteDescription(offer)
③pc2CreateAnswer → SetLocalDescription(answer)
④pc1SetRemoteDescription(answer)

SDP 실물은 실습에서 직접 찍는다. 미리 해독표 — 아래는 이번 실습의 실측 offer에서 뽑은 줄들이다:

v=0                          ← SDP 버전 (항상 0)
o=- 88142078039991151 ...    ← origin: 세션 식별자
s=-                          ← 세션 이름 (안 씀)
t=0 0                        ← 유효 시간 (0 0 = 무제한)
a=fingerprint:sha-256 6E:5B:...  ← DTLS 인증서 지문 (보안 — 레슨 0017)
m=application 9 UDP/DTLS/SCTP webrtc-datachannel
                             ← 미디어 섹션: "데이터 채널을 하겠다"
a=ice-ufrag:oHaiUHzVVuosEOPX ← ICE 자격 증명 (연결 수립 — 레슨 0016)
a=candidate:... typ host ... ← 연결 후보 주소 (레슨 0016)

m= 라인이 "이 연결로 무엇을 주고받을지"(미디어/데이터)를 선언하는 섹션의 시작이다 — 영상 트랙을 추가하면 m=video 섹션이 생긴다 (레슨 0018).

3. PeerConnection의 상태 머신 — 세 개가 따로 돈다

상태 머신주요 상태말해주는 것
SignalingState
OnSignalingStateChange		stable → have-local-offer / have-remote-offer → stableSDP 교환이 어디까지 진행됐나
ICEConnectionState
OnICEConnectionStateChange		new → checking → connected / failed네트워크 경로를 찾았나 (레슨 0016)
PeerConnectionState
OnConnectionStateChange		new → connecting → connected / failed / closed종합 판정 — 실무에서 보는 최종 신호

함정: signaling이 stable이어도 연결된 게 아니다. stable은 "SDP 교환을 마쳤다"일 뿐이고, 실제 연결 성립은 PeerConnectionState가 connected가 되는 순간이다 — 실습 로그에서 두 시점이 분리되어 보인다.

4. 실습 — 한 프로세스, 두 피어

시그널링 서버를 만드는 대신 한 프로세스 안에 피어 두 개를 만들어 SDP를 변수로 전달한다. 프로토콜 학습에서 네트워크 잡음을 제거하는 이 패턴이 이번 아크 실습 전체의 뼈대다.

  1. playground/webrtc-basics를 만들고 모듈 초기화 후 첫 외부 의존성을 설치: 
    go mod init webrtcbasics
go get github.com/pion/webrtc/v4

    예상: go: added github.com/pion/webrtc/v4 v4.2.18 등 — go.mod에 require 블록이 생긴다 (레슨 0008의 모듈 지식이 여기서 실전이 된다). 이 레슨의 실측은 v4.2.18 기준.

  2. main.go 작성: 
    package main

import (
	"fmt"
	"strings"
	"time"

	"github.com/pion/webrtc/v4"
)

// wireStateLogs는 피어의 3가지 상태 머신 전이를 라벨과 함께 출력한다.
func wireStateLogs(label string, pc *webrtc.PeerConnection) {
	pc.OnSignalingStateChange(func(s webrtc.SignalingState) {
		fmt.Printf("[%s] signaling → %s\n", label, s)
	})
	pc.OnICEConnectionStateChange(func(s webrtc.ICEConnectionState) {
		fmt.Printf("[%s] ice       → %s\n", label, s)
	})
	pc.OnConnectionStateChange(func(s webrtc.PeerConnectionState) {
		fmt.Printf("[%s] conn      → %s\n", label, s)
	})
}

// run은 한 프로세스 안에서 두 피어를 만들어 offer/answer를 교환하고
// 데이터 채널로 ping-pong 왕복이 성공하면 nil을 반환한다.
func run() error {
	pc1, err := webrtc.NewPeerConnection(webrtc.Configuration{})
	if err != nil {
		return fmt.Errorf("pc1 생성: %w", err)
	}
	defer pc1.Close()

	pc2, err := webrtc.NewPeerConnection(webrtc.Configuration{})
	if err != nil {
		return fmt.Errorf("pc2 생성: %w", err)
	}
	defer pc2.Close()

	wireStateLogs("pc1", pc1)
	wireStateLogs("pc2", pc2)

	done := make(chan struct{})

	// pc1이 데이터 채널을 연다 — 연결이 열리면 ping을 보낸다.
	dc, err := pc1.CreateDataChannel("greeting", nil)
	if err != nil {
		return fmt.Errorf("데이터 채널 생성: %w", err)
	}
	dc.OnOpen(func() {
		fmt.Println("[pc1] 데이터 채널 열림 — ping 송신")
		dc.SendText("ping from pc1")
	})
	dc.OnMessage(func(m webrtc.DataChannelMessage) {
		fmt.Printf("[pc1] 수신: %s\n", string(m.Data))
		close(done)
	})

	// pc2는 상대가 연 채널을 받아 pong으로 응답한다.
	pc2.OnDataChannel(func(d *webrtc.DataChannel) {
		d.OnMessage(func(m webrtc.DataChannelMessage) {
			fmt.Printf("[pc2] 수신: %s\n", string(m.Data))
			d.SendText("pong from pc2")
		})
	})

	// ── 시그널링 서버 대신 변수로 SDP를 전달한다: offer → answer ──
	offer, err := pc1.CreateOffer(nil)
	if err != nil {
		return fmt.Errorf("offer 생성: %w", err)
	}
	g1 := webrtc.GatheringCompletePromise(pc1)
	if err := pc1.SetLocalDescription(offer); err != nil {
		return fmt.Errorf("pc1 local 설정: %w", err)
	}
	<-g1 // non-trickle: candidate 수집이 끝난 완전한 SDP를 기다린다 (레슨 0016)

	fmt.Println("--- pc1 offer SDP 앞 6줄 ---")
	for _, line := range strings.SplitN(pc1.LocalDescription().SDP, "\r\n", 7)[:6] {
		fmt.Println(line)
	}

	if err := pc2.SetRemoteDescription(*pc1.LocalDescription()); err != nil {
		return fmt.Errorf("pc2 remote 설정: %w", err)
	}
	answer, err := pc2.CreateAnswer(nil)
	if err != nil {
		return fmt.Errorf("answer 생성: %w", err)
	}
	g2 := webrtc.GatheringCompletePromise(pc2)
	if err := pc2.SetLocalDescription(answer); err != nil {
		return fmt.Errorf("pc2 local 설정: %w", err)
	}
	<-g2
	if err := pc1.SetRemoteDescription(*pc2.LocalDescription()); err != nil {
		return fmt.Errorf("pc1 remote 설정: %w", err)
	}

	select {
	case <-done:
		fmt.Println("왕복 성공 — WebRTC 연결로 데이터가 오갔다")
		return nil
	case <-time.After(10 * time.Second):
		return fmt.Errorf("타임아웃: 연결 실패")
	}
}

func main() {
	if err := run(); err != nil {
		fmt.Println("에러:", err)
	}
}

    낯익은 재료뿐이다: 콜백은 함수 값(레슨 0006의 감각), done 채널과 select 타임아웃(레슨 0007·0011), %w 래핑(레슨 0003). SDP는 \r\n 줄바꿈을 쓴다는 것만 새롭다.

  3. 실행: 
    go run .

    실측 출력 (candidate 수집 타이밍에 따라 줄 순서는 약간 다를 수 있다):

    [pc1] signaling → have-local-offer
--- pc1 offer SDP 앞 6줄 ---
v=0
o=- 88142078039991151 1787269946 IN IP4 0.0.0.0
s=-
t=0 0
a=msid-semantic:WMS *
a=fingerprint:sha-256 6E:5B:6C:7F:...
[pc2] signaling → have-remote-offer
[pc2] signaling → stable
[pc2] ice       → checking
[pc2] conn      → connecting
[pc1] signaling → stable
[pc1] ice       → checking
[pc1] conn      → connecting
[pc2] ice       → connected
[pc1] ice       → connected
[pc1] conn      → connected
[pc2] conn      → connected
[pc1] 데이터 채널 열림 — ping 송신
[pc2] 수신: ping from pc1
[pc1] 수신: pong from pc2
왕복 성공 — WebRTC 연결로 데이터가 오갔다

    §3의 함정이 로그에 그대로 있다: 양쪽 signaling이 stable이 된 뒤에도 ice checking → conn connecting을 거쳐야 connected가 된다.

부숴보기 — 프로토콜은 순서에 엄격하다

  1. 마지막 단계인 pc1.SetRemoteDescription(*pc2.LocalDescription()) 블록을 지우고 실행 — answer가 전달되지 않으면?

    실측: pc1은 signaling → have-local-offer에서 영원히 멈추고, answer를 만든 pc2만 ice → checking을 시도하다 응답을 못 받는다. 10초 뒤 에러: 타임아웃: 연결 실패. 시그널링이 반쪽이면 연결은 절대 성립하지 않는다 — 실무에서 "offer는 갔는데 연결이 안 돼요"의 1순위 용의자. 확인 후 원상복구.

  2. 새 파일에서 remote offer를 넣기 전에 pc2.CreateAnswer(nil)부터 호출해 보면: 
    CreateAnswer 에러: InvalidStateError: remote description is not set

    answer는 "offer에 대한 응답"이라 offer 없이는 만들 수조차 없다 — §2 표의 ②→③ 순서를 라이브러리가 강제한다. 에러 이름 InvalidStateError는 W3C 표준 용어 그대로다.
