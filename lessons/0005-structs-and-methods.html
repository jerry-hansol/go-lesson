Lesson 0005 · Go 기초

구조체·메서드·포인터 — 클래스 없이 사는 법

MediaMTX 코드를 열면 type Stream struct와 func (s *Stream) ...가 도배되어 있다. 오늘은 그 두 문법이 전부다: 데이터 묶음(구조체), 명시적 공유(포인터), 동작 붙이기(메서드). 예상 소요: 35–40분.

오늘의 목표 (하나만)

상태를 가진 Stream 타입에 메서드를 붙여보고, 값 리시버와 포인터 리시버 중 무엇을 언제 쓰는지 근거를 들어 설명할 수 있다.

1. 구조체 — 클래스가 아니라 데이터 묶음

type Stream struct {
    Name        string
    BitrateKbps int
    Live        bool
}

s1 := Stream{Name: "ebay-live-1", BitrateKbps: 3000}  // 필드명 명시 (권장)
var s2 Stream   // 모든 필드가 zero value — 이대로 바로 사용 가능

Java 클래스에서 익숙한 것들이 여기엔 없다 — 그리고 그게 설계다 (Go by Example: Structs):

JavaGo
상속 (extends)없음 — 합성으로 해결 (임베딩은 추후 레슨)
생성자 (new Stream(...))없음 — 리터럴 또는 NewStream 함수 관례 (§4)
getter/setter없음 — 필드 직접 접근. 첫 글자 대문자 = 공개 (레슨 0001 규칙 그대로)
초기화 안 하면 nullzero value로 채워진 즉시 사용 가능한 값

2. 포인터 — Java의 암묵적 참조를 명시적으로

Java에서 객체 변수는 전부 참조라서 대입·전달이 곧 공유다. Go는 반대다: 대입은 값 복사가 기본이고, 공유하고 싶으면 포인터 *Stream을 명시해야 한다 (Go by Example: Pointers).

p := &s1          // & — s1의 주소를 얻는다. p의 타입은 *Stream
p.BitrateKbps = 4000   // 포인터를 통해 원본 수정 ((*p).BitrateKbps의 단축 표기)

var q *Stream     // 포인터의 zero value는 nil — 역참조하면 panic (부숴보기에서 확인)

C를 기억하는 분을 위해: 포인터 연산(p++)은 없다. 주소를 얻고(&) 따라가는(*) 것만 가능해서, Java만큼 안전하면서 복사/공유가 코드에 드러난다.

3. 메서드와 리시버 — 값이냐 포인터냐

메서드는 클래스 안이 아니라 함수 앞의 리시버로 정의한다. 리시버가 Java의 this다 (Go by Example: Methods):

func (s *Stream) Start() {   // 포인터 리시버 — 원본의 상태를 바꾼다
    s.Live = true
}

func (s Stream) Describe() string {   // 값 리시버 — 복사본을 읽기만 한다
    ...
}

선택 기준은 공식 FAQ가 명확하다 (Go FAQ: Should I define methods on values or pointers?):

상황리시버
메서드가 상태를 수정한다포인터 (필수) — 값 리시버는 복사본만 바꾼다
구조체가 크다 (복사 비용)포인터
메서드 중 하나라도 포인터가 필요하다전부 포인터로 통일 (일관성)
작고 읽기만 한다값도 OK

호출은 어느 쪽이든 s.Start()로 쓴다 — 컴파일러가 &s/*s를 자동으로 맞춰준다. 문법은 편하지만 의미(원본 수정 여부)는 리시버 선언이 결정한다는 게 오늘의 핵심.

4. 생성자 관례 — NewX

zero value로 충분하면 리터럴로 끝. 초기화 로직이 필요할 때만 New 접두사 함수를 만든다 — 키워드가 아니라 순전히 관례다:

// NewStream은 기본 비트레이트로 초기화된 Stream을 반환한다.
func NewStream(name string) *Stream {
    return &Stream{Name: name, BitrateKbps: 3000}
}

5. 실습 — 스트림 상태 머신

  1. playground/structs 디렉토리를 만들고 go mod init streams

    모듈명을 structs로 하면 Go 1.26 표준 라이브러리의 structs 패키지와 충돌해 ambiguous import 에러가 난다 — 실측 확인. 표준 라이브러리와 겹치지 않는 이름을 쓰자.

  2. main.go 작성: 
    package main

import "fmt"

// Stream은 방송 스트림 하나의 상태를 담는다.
type Stream struct {
	Name        string
	BitrateKbps int
	Live        bool
}

// NewStream은 기본 비트레이트로 초기화된 Stream을 반환한다 (생성자 관례).
func NewStream(name string) *Stream {
	return &Stream{Name: name, BitrateKbps: 3000}
}

// Start는 스트림을 송출 상태로 바꾼다 — 상태를 바꾸므로 포인터 리시버.
func (s *Stream) Start() {
	s.Live = true
}

// Stop은 스트림 송출을 중단한다.
func (s *Stream) Stop() {
	s.Live = false
}

// Describe는 현재 상태를 한 줄로 요약한다 — 읽기만 하므로 값 리시버.
// (실무에선 Start/Stop이 포인터라 통일하는 편 — 본문 일관성 규칙 참고)
func (s Stream) Describe() string {
	state := "대기 중"
	if s.Live {
		state = "송출 중"
	}
	return fmt.Sprintf("%s (%d kbps) — %s", s.Name, s.BitrateKbps, state)
}

func main() {
	s := NewStream("ebay-live-1")
	fmt.Println(s.Describe())

	s.Start()
	fmt.Println(s.Describe())

	s.Stop()
	fmt.Println(s.Describe())
}
  3. go run .

    예상 출력 (실측):
    ebay-live-1 (3000 kbps) — 대기 중
    ebay-live-1 (3000 kbps) — 송출 중
    ebay-live-1 (3000 kbps) — 대기 중

부숴보기 — 이번에도 세 가지

  1. Start의 리시버에서 *만 지우기: func (s Stream) Start()

    실측: 에러 없이 컴파일되고 세 줄 전부 "대기 중"이 나온다. 값 리시버가 복사본의 Live만 바꾸는 조용한 버그 — Go 입문자가 가장 많이 밟는 함정이다. 확인 후 원상복구.

  2. 새 파일 실험: var s *Stream 선언만 하고 fmt.Println(s.Name)

    실측: panic: runtime error: invalid memory address or nil pointer dereference + [signal SIGSEGV ...] + 고루틴 스택. Go의 NPE다 — panic 메시지에서 파일:라인을 읽는 연습. 확인 후 삭제.

  3. 리터럴에 없는 필드 쓰기: Stream{Name: "x", Codec: "h264"}

    실측: unknown field Codec in struct literal of type Stream — 컴파일 타임에 잡힌다. 원상복구 후 go fmt ./...로 마무리.
