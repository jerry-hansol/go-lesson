Lesson 0012 · Go 실전

공유 상태와 레이스 — 채널만으로 다 되진 않는다

미디어 서버의 세션 맵, 시청자 카운터 같은 공유 상태는 채널이 아니라 뮤텍스의 영역이다. 오늘은 레이스 버그를 직접 만들고, 도구로 검출하고, 수리하는 전체 사이클을 돈다. 예상 소요: 40분.

오늘의 목표 (하나만)

데이터 레이스를 go run -race로 검출하고 sync.Mutex로 수리할 수 있다 — 재현 → 검출 → 수리 사이클을 내 손으로 한 바퀴.

1. 데이터 레이스 — 재현이 안 되는 버그

고루틴 둘 이상이 같은 메모리를 동기화 없이 접근하고 그중 하나라도 쓰기면 데이터 레이스다. 무서운 건 증상이다 — 크래시가 아니라 조용히 틀린 값이 나온다. 고루틴 100개가 total++를 1,000번씩 실행한 실측 결과:

기대: 100000, 실제: 44265   // 1회차
기대: 100000, 실제: 45324   // 2회차
기대: 100000, 실제: 45091   // 3회차 — 매번 다르고, 에러도 경고도 없다

++는 읽기→더하기→쓰기 3단계라서 고루틴끼리 서로의 쓰기를 덮어쓴다. 타이밍에 의존하므로 로컬에선 멀쩡하다가 트래픽 많은 프로덕션에서만 터진다.

Go의 무기는 레이스 디텍터다: go run -race / go test -race 플래그 하나로 실행 중의 레이스를 검출한다. JVM에는 이런 도구가 표준 툴체인에 없다 — Java에서 외부 분석 도구로 하던 일이 Go에선 내장이다. 오버헤드(실행·메모리 수 배)가 있으니 개발·CI 전용이고 프로덕션 빌드엔 쓰지 않는다.

2. sync.Mutex — 공유 상태의 자물쇠

// Store는 스트림별 시청자 수를 보관한다.
// 뮤텍스는 보호 대상 필드 바로 위에 — 한 몸으로 묶는 관례.
type Store struct {
    mu      sync.Mutex
    viewers map[string]int
}

// Add는 스트림의 시청자 수를 n만큼 더한다.
func (s *Store) Add(stream string, n int) {
    s.mu.Lock()
    defer s.mu.Unlock()   // Lock 직후 defer로 예약 — 어떤 리턴 경로든 풀린다
    s.viewers[stream] += n
}
  • Lock() 직후 defer Unlock() — 레슨 0003의 defer가 여기서 빛난다.
  • 리시버는 반드시 포인터(레슨 0005 규칙의 실전 사례) — 값 리시버면 뮤텍스가 복사돼 자물쇠가 여러 개가 된다. go vet이 이 실수를 copylocks 검사로 잡는다.
  • Java synchronized/ReentrantLock에 대응하지만 Go 뮤텍스는 재진입 불가 — 같은 고루틴이 두 번 Lock하면 자기 자신을 기다리다 죽는다 (부숴보기에서 직접 확인).
  • 읽기가 쓰기보다 훨씬 잦으면 sync.RWMutex — RLock()은 여러 고루틴이 동시에 잡을 수 있다. 시청자 수 조회가 갱신보다 잦은 전형적인 케이스.
  • 한 줄 소개만: sync.Once는 "딱 한 번 초기화" 보장, sync/atomic은 단일 정수 카운터라면 뮤텍스보다 가벼운 원자 연산.

3. 채널이냐 뮤텍스냐

Effective Go의 슬로건 — "메모리를 공유해서 통신하지 말고, 통신해서 메모리를 공유하라" — 는 소유권 이전에 대한 이야기다. 모든 공유 상태를 채널로 바꾸라는 뜻이 아니다.

상황도구미디어 서버 예
데이터의 소유권을 넘기는 파이프라인채널세그먼트를 워커에게 전달 (레슨 0007)
여러 고루틴이 같은 상태를 짧게 읽고 쓰기뮤텍스세션 맵, 시청자 카운터, 설정 캐시

실무 미디어 서버의 세션 레지스트리는 대부분 RWMutex + 맵이다 — 채널로 짜면 오히려 복잡해진다.

4. 실습 — 재현 → 검출 → 수리

  1. playground/streamstore를 만들고 go mod init streamstore (표준 라이브러리와 충돌 없는 이름 — 레슨 0005의 함정 기억). 먼저 보호 없는 버전을 작성: 
    package main

import (
	"fmt"
	"sync"
)

// Store는 스트림별 시청자 수를 보관한다 — 아직 보호 장치가 없다.
type Store struct {
	viewers map[string]int
}

func main() {
	s := Store{viewers: make(map[string]int)}
	var wg sync.WaitGroup

	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			s.viewers["ebay-live-42"]++ // 읽고-더하고-쓰기, 보호 없음
		}()
	}
	wg.Wait()
	fmt.Println("시청자 수:", s.viewers["ebay-live-42"])
}
  2. 레이스 디텍터로 실행: go run -race .

    예상: WARNING: DATA RACE 블록이 여러 개 — 각 블록이 "누가 읽었나(Read at ... by goroutine 9)"와 "직전에 누가 썼나(Previous write ... by goroutine 7)"를 파일:줄 번호까지 짚어준다 (여기선 main.go:21, 바로 ++ 줄). 실측 실행에서는 레이스 4건 검출 + 카운트도 시청자 수: 65로 틀렸고, 마지막 줄 Found 4 data race(s)와 함께 exit status 66으로 종료됐다 — fatal 크래시가 아니라 "보고 후 비정상 종료 코드"다.

  3. 2절의 Mutex 패턴으로 수리 — Store에 mu sync.Mutex를 넣고 Add/Count 메서드로 접근을 감싼 뒤(위 2절 코드 그대로, 생성자 NewStore() 포함) main에서는 s.Add("ebay-live-42", 1)을 호출: 
    go run -race .

    예상: 시청자 수: 100, 경고 0건, 종료 코드 0. 실측 3회 연속 정확히 100 — 이게 수리 완료의 증거다. go vet .도 깨끗.

부숴보기 — 동시성 사고 3종

  1. 수리 버전에 func report(s Store) 처럼 Store를 값으로 받는 함수를 추가하고 go vet .

    예상 (실측): report passes lock by value: streamstore.Store contains sync.Mutex + 호출부에도 call of report copies lock value — 뮤텍스 복사는 컴파일은 되지만 vet이 잡는다. 단, vet은 이 실수 패턴을 잡을 뿐 레이스 자체는 못 잡는다 — 레이스는 -race의 몫. 확인 후 삭제.

  2. 같은 고루틴에서 mu.Lock()을 두 번 연속 호출하고 실행:

    예상 (실측): fatal error: all goroutines are asleep - deadlock! + 스택에 goroutine 1 [sync.Mutex.Lock] — 재진입 불가라서 자기 자신을 기다리다 런타임이 즉사시킨다 (레슨 0007의 데드락 검출과 같은 메커니즘). 확인 후 삭제.

  3. 1단계의 보호 없는 버전을 -race 없이 go run .으로 실행:

    예상 (실측 3/3회): fatal error: concurrent map writes — 맵만큼은 런타임이 자체 검사로 잡아준다. 하지만 §1의 int 카운터(44265...)는 아무도 안 잡아줬다는 걸 기억하자 — 런타임의 맵 검사는 보너스일 뿐, 보증은 -race와 뮤텍스가 한다.
