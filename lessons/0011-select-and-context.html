Lesson 0011 · Go 실전

select와 context — 멈출 줄 아는 동시성

레슨 0007에서 고루틴을 시작하는 법을 배웠다. 실무의 나머지 절반은 멈추는 법이다 — 시청자가 플레이어를 닫았는데 서버가 트랜스코딩을 계속하면 그게 리소스 누수다. 예상 소요: 40분.

오늘의 목표 (하나만)

context.WithTimeout으로 느린 트랜스코딩 워커를 끊는 파이프라인을 작성하고, ctx.Done()/ctx.Err()와 defer cancel() 관례를 설명할 수 있다.

1. select — 여러 채널을 동시에 기다린다

switch처럼 생겼지만 대상이 값이 아니라 채널 연산이다. 준비된 case가 실행되고, 없으면 블록된다. Java라면 Selector나 폴링 루프를 짜야 할 일이 언어 문법 하나로 끝난다 (Go by Example: Select).

ch := make(chan string)
go func() {
    time.Sleep(200 * time.Millisecond)
    ch <- "keyframe"
}()

select {
case v := <-ch:
    fmt.Println("받음:", v)
case <-time.After(100 * time.Millisecond):   // ① 타임아웃 패턴
    fmt.Println("타임아웃 — 스트림이 늦는다")
}

select {
case v := <-ch:
    fmt.Println("받음:", v)
default:                                      // ② 논블로킹 패턴
    fmt.Println("지금은 없음 — 논블로킹")
}

실제 출력: 타임아웃 — 스트림이 늦는다 / 지금은 없음 — 논블로킹 (keyframe은 200ms 뒤에나 오므로 둘 다 못 받는다. Go by Example: Timeouts)

두 case가 동시에 준비되면? 위의 것이 아니라 무작위로 하나가 실행된다 — 한 채널만 계속 선택되는 기아(starvation)를 막는 의도적 설계다.

2. context — 취소를 전파하는 트리

Java에 대응물이 없는, Go 실무의 필수 관례다. Thread.interrupt()가 스레드 하나를 찌르는 것이라면, context는 요청 하나에 얽힌 고루틴 전부에 "그만"을 방송하는 트리다 (Go Concurrency Patterns: Context — Sameer Ajmani).

ctx := context.Background()                       // 루트 — 절대 취소되지 않음
ctx, cancel := context.WithCancel(ctx)            // 수동 취소 가능한 자식
ctx, cancel := context.WithTimeout(ctx, 2*time.Second)  // 시한부 자식
  • ctx.Done() — 취소되면 닫히는 채널을 돌려준다. 닫힌 채널 수신은 즉시 리턴하므로(레슨 0007) select의 case로 바로 쓴다.
  • ctx.Err() — 취소 사유. 수동 취소면 context.Canceled, 시한 초과면 context.DeadlineExceeded.
  • 부모가 취소되면 모든 자손이 함께 취소된다 — 그래서 실무 Go 함수 대부분의 시그니처가 func f(ctx context.Context, ...)로 시작한다. 받았으면 아래로 계속 넘기는 것이 규칙.
  • cancel을 받았으면 반드시 defer cancel() — 타임아웃이 나더라도 타이머 리소스를 해제해야 한다. 안 지키면 go vet이 잡아낸다 (부숴보기 1).

3. HTTP와의 연결 — 시청자가 나가면 ctx가 닫힌다

이게 실무에서 context를 만나는 첫 지점이다. 핸들러의 r.Context()는 클라이언트가 연결을 끊는 순간 취소된다 (Go by Example: Context):

http.HandleFunc("/stream", func(w http.ResponseWriter, r *http.Request) {
    select {
    case <-time.After(5 * time.Second):        // 느린 세그먼트 생성 흉내
        fmt.Fprintln(w, "세그먼트 전송 완료")
    case <-r.Context().Done():                 // 시청자 이탈
        fmt.Println("클라이언트 이탈 감지:", r.Context().Err())
    }
})

실측: 이 서버에 curl --max-time 1로 요청을 걸고 1초에 끊으면 서버 로그에 클라이언트 이탈 감지: context canceled가 찍힌다. 5초짜리 작업이 1초 만에 정리된 것 — 이 ctx를 트랜스코더까지 넘기면 파이프라인 전체가 함께 멈춘다.

4. 실습 — 취소에 반응하는 트랜스코딩 파이프라인

  1. playground/pipeline을 만들고 go mod init pipeline 후 main.go 작성: 
    package main

import (
	"context"
	"fmt"
	"time"
)

// transcode는 세그먼트들을 순서대로 처리해 results로 보내되,
// ctx가 취소되면 하던 일을 버리고 즉시 리턴한다.
func transcode(ctx context.Context, segs []string, results chan<- string) {
	defer close(results) // 생산자가 닫는다
	for _, seg := range segs {
		select {
		case <-time.After(600 * time.Millisecond): // 세그먼트 처리 흉내
			results <- seg + " 완료"
		case <-ctx.Done(): // 타임아웃·클라이언트 이탈
			fmt.Println("트랜스코더 중단:", ctx.Err())
			return
		}
	}
}

func main() {
	// 이 작업 전체는 1.5초 안에 끝나야 한다고 선언
	ctx, cancel := context.WithTimeout(context.Background(), 1500*time.Millisecond)
	defer cancel() // 관례: 만들었으면 반드시 defer cancel()

	results := make(chan string)
	go transcode(ctx, []string{"seg-1", "seg-2", "seg-3", "seg-4"}, results)

	start := time.Now()
	for r := range results { // 채널이 닫히면 루프 종료
		fmt.Println(r, time.Since(start).Round(100*time.Millisecond))
	}
}
  2. go run .

    실제 출력: seg-1 완료 600ms → seg-2 완료 1.2s → 트랜스코더 중단: context deadline exceeded. 1.5초 시한이 seg-3 처리 중(1.8s 예정)에 걸려 나머지가 통째로 취소됐다. HTTP 데모의 context canceled와 사유가 다른 것에 주목 — ctx.Err()가 원인을 구분해 준다.

  3. 타임아웃을 3*time.Second로 늘리고 다시 실행:

    실제 출력: seg-1 완료 600ms ~ seg-4 완료 2.4s — 4개 전부 완료. 같은 코드가 시한 안에서는 끝까지, 시한 밖에서는 깨끗하게 중단된다. 확인 후 1500ms로 원상복구.

부숴보기 — 동시성 사고 2제

  1. ctx, cancel := ...에서 cancel을 _로 버리고 go vet ./...

    실측: the cancel function returned by context.WithTimeout should be called, not discarded, to avoid a context leak — 컴파일은 되지만 vet이 잡는 리소스 누수. defer cancel()로 원상복구.

  2. 닫힌 채널은 select에서 항상 준비 상태다 — 새 파일로 확인: 
    ch := make(chan int)
close(ch)
for i := 1; i <= 3; i++ {
    select {
    case v := <-ch:
        fmt.Printf("%d번째 수신: %d (즉시)\n", i, v)
    case <-time.After(time.Second):
        fmt.Println("타임아웃")
    }
}

    실측: 3초 걸릴 것 같지만 0.1초 만에 1~3번째 수신: 0 (즉시) — 타임아웃 case는 한 번도 실행되지 않는다. 실무에서 이게 "닫힌 채널을 계속 읽는 CPU 100% 무한 루프" 사고가 된다. 탈출법(v, ok + nil 채널 트릭)은 치트시트에.

한 줄 경고: 오래 도는 루프 안에서 매번 time.After로 새 타이머를 만드는 것은 낭비다 — 재사용이 필요하면 time.NewTimer(심화에서 다룬다).
