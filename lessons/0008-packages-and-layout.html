Lesson 0008 · Go 실전

패키지와 프로젝트 구조 — mediamtx가 읽히는 지도

기초 아크 졸업, 실전 아크 시작. 지금까지는 파일 하나였지만 실제 미디어 서버는 수백 개 패키지다. 오늘은 그 지도를 그리는 법 — 읽는 데서 끝나지 않고 직접 만든다. 예상 소요: 35–40분.

오늘의 목표 (하나만)

cmd/와 internal/로 나뉜 멀티 패키지 모듈을 직접 만들어 실행하고, mediamtx·livekit 저장소를 열었을 때 어디에 무엇이 있는지 예측할 수 있다.

1. 디렉토리 = 패키지, import 경로 = 모듈경로/디렉토리

레슨 0001에서 "같은 디렉토리 = 같은 패키지"를 봤다. 멀티 패키지가 되면 규칙이 하나 추가될 뿐이다: import 경로는 모듈 경로 + 디렉토리 경로다 (How to Write Go Code).

mediakit/                      ← go.mod: module mediakit
├── internal/segment/          ← import "mediakit/internal/segment"
└── cmd/streamctl/             ← package main (진입점)

Java와 대비하면: Maven 좌표(groupId/artifactId)와 package 선언이라는 이중 체계 대신, 경로 하나가 전부다. 같은 모듈 안이면 go.mod에 의존성 선언 없이 바로 import된다. 관례상 패키지 이름은 디렉토리 이름과 같게 하고, 사용할 때는 segment.SplitSegments(...)처럼 패키지명이 접두어가 된다.

2. 대문자/소문자 = 패키지 API 설계

레슨 0001의 "대문자 = 공개" 규칙이 여기서 진짜 의미를 갖는다. 한 패키지의 exported 식별자 집합이 곧 그 패키지의 public API다. Java에서 인터페이스와 private로 하던 캡슐화 설계를, Go에서는 이름 첫 글자로 한다:

  • SplitSegments — 밖에서 쓰라고 내놓은 계약
  • normalize — 패키지 내부 구현. 밖에서는 보이지도 않는다 (부숴보기에서 확인)

3. 표준 레이아웃: cmd/ 와 internal/

공식 가이드 Organizing a Go module이 권하는 구조는 단순하다:

디렉토리역할강제성
cmd/<이름>/main.go바이너리 진입점. 바이너리가 여러 개면 cmd/ 아래 나란히관례
internal/이 모듈 전용 코드. 외부 모듈이 import하면 컴파일 에러컴파일러가 강제
pkg/외부 공개 라이브러리를 모으는 관례 — 논쟁이 있고, 공식 문서는 굳이 권하지 않는다. 한 줄만 알면 된다관례

미션 연결 — 실제로 열어 보면: mediamtx는 루트 main.go 하나 + 코드 전부를 internal/ 아래에 두고(외부에 API를 약속하지 않겠다는 선언), livekit은 cmd/ + pkg/ 구조다. 오늘 배우는 세 조각이 그대로 두 저장소의 지도다.

4. 실습 — mediakit 모듈 만들기

레슨 0002의 splitSegments와 0003의 parseResolution을 재사용 가능한 패키지로 승격시킨다.

  1. 구조를 만들고 모듈 초기화: 
    mkdir -p ~/Desktop/repo/learn-go/playground/mediakit/internal/segment
mkdir -p ~/Desktop/repo/learn-go/playground/mediakit/cmd/streamctl
cd ~/Desktop/repo/learn-go/playground/mediakit
go mod init mediakit
  2. internal/segment/segment.go 작성: 
    // Package segment는 스트림 재생 시간과 해상도를 다루는 유틸리티다.
package segment

import (
	"fmt"
	"strconv"
	"strings"
)

// SplitSegments는 총 재생 시간(초)을 세그먼트 길이로 나눠
// 온전한 세그먼트 개수와 남는 초를 반환한다.
func SplitSegments(totalSec, segLen int) (int, int) {
	return totalSec / segLen, totalSec % segLen
}

// ParseResolution은 "1920x1080" 형태의 문자열을 가로·세로 정수로 파싱한다.
func ParseResolution(s string) (int, int, error) {
	parts := strings.Split(s, "x")
	if len(parts) != 2 {
		return 0, 0, fmt.Errorf("해상도 형식이 아님: %q", s)
	}
	w, err := strconv.Atoi(parts[0])
	if err != nil {
		return 0, 0, fmt.Errorf("가로 파싱 실패: %w", err)
	}
	h, err := strconv.Atoi(parts[1])
	if err != nil {
		return 0, 0, fmt.Errorf("세로 파싱 실패: %w", err)
	}
	return w, h, nil
}

// normalize는 세그먼트 길이를 허용 범위(2~10초)로 보정한다.
// 소문자 시작 = 패키지 내부 전용(unexported).
func normalize(segLen int) int {
	if segLen < 2 {
		return 2
	}
	if segLen > 10 {
		return 10
	}
	return segLen
}
  3. cmd/streamctl/main.go 작성: 
    // streamctl은 mediakit 라이브러리를 사용하는 CLI 진입점이다.
package main

import (
	"fmt"
	"os"

	"mediakit/internal/segment"
)

func main() {
	full, rem := segment.SplitSegments(95, 6)
	fmt.Println("세그먼트:", full, "개, 마지막:", rem, "초")

	w, h, err := segment.ParseResolution("1920x1080")
	if err != nil {
		fmt.Fprintln(os.Stderr, "에러:", err)
		os.Exit(1)
	}
	fmt.Printf("해상도: %d×%d (비율 %.2f:1)\n", w, h, float64(w)/float64(h))
}
  4. 모듈 루트에서 실행 — 패키지 경로로 실행하는 것에 주목: 
    go run ./cmd/streamctl

    예상 출력: 세그먼트: 15 개, 마지막: 5 초 / 해상도: 1920×1080 (비율 1.78:1). go build ./cmd/streamctl이면 streamctl 바이너리가 남는다 — 바이너리가 여러 개인 프로젝트에서 이 패턴이 표준이다.

부숴보기 — 경계가 진짜 벽인지 확인한다

  1. internal 침범: playground/outsider라는 별도 모듈을 만들어 남의 internal을 훔쳐 써 본다. outsider/go.mod: 
    module outsider

go 1.26

require mediakit v0.0.0

replace mediakit => ../mediakit
    outsider/main.go에서 "mediakit/internal/segment"를 import하고 go run .:

    예상: main.go:7:2: use of internal package mediakit/internal/segment not allowed — 관례가 아니라 컴파일러가 거부한다. mediamtx가 코드 전부를 internal에 두는 이유다. (replace는 로컬 디렉토리로 의존성을 돌리는 개발용 지시자 — 덤으로 배웠다.)

  2. unexported 접근: cmd/streamctl/main.go에 _ = segment.normalize 한 줄을 추가하고 go build ./...:

    예상: undefined: segment.normalize — "금지됐다"가 아니라 "존재하지 않는다"고 나온다. 소문자 식별자는 패키지 밖에서 보이지도 않는다. 확인 후 원상복구.
