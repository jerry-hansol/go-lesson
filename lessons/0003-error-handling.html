Lesson 0003 · Go 기초

에러 처리 — 예외 없는 언어에서 사는 법

Go에는 try/catch가 없다. 레슨 0002의 다중 반환이 여기서 진가를 발휘한다: 에러는 던지는(throw) 게 아니라 반환하는 값이다. 예상 소요: 35–40분.

오늘의 목표 (하나만)

해상도 문자열 파서를 (값, error) 관례로 작성하고, %w 래핑이 errors.Is 검사를 가능하게 하는 이유를 설명할 수 있다.

1. 에러는 값이다

error는 특별한 문법이 아니라 그냥 타입이다(정확히는 메서드 하나짜리 인터페이스 — 인터페이스 자체는 레슨 0006에서). 실패할 수 있는 함수는 마지막 반환값으로 error를 돌려주고, 성공이면 nil을 준다:

w, h, err := parseResolution("1920x1080")
if err != nil {
    // 처리하거나, 감싸서 위로 반환하거나
    return err
}
// 여기부터는 성공 경로 — 들여쓰기가 깊어지지 않는다
JavaGo
throw / try-catch — 에러가 별도의 제어 흐름에러가 반환값 — 일반 코드와 같은 흐름
checked exception을 컴파일러가 강제강제는 없지만, 받은 err를 안 쓰면 컴파일 에러 → 사실상 무시 불가
스택 트레이스로 원인 추적래핑 체인(%w)으로 원인 추적

이 if err != nil { return } 조기 반환이 Go 코드의 표준 리듬이다. MediaMTX 같은 코드베이스를 열면 이 패턴이 페이지마다 보일 것이다 (Errors are values — Rob Pike).

2. 에러 만들기 · 감싸기 · 검사하기

errors.New("스트림이 이미 종료됨")            // 고정 메시지 에러
fmt.Errorf("세션 %d 없음", id)                // 포맷 에러
fmt.Errorf("가로 값 파싱 실패: %w", err)       // ★ %w — 원인 에러를 안에 보존(래핑)

errors.Is(err, strconv.ErrSyntax)             // 래핑 체인 어딘가에 이 에러가 있나?

핵심은 %w다. %v로 포맷하면 원인 에러가 문자열로 녹아버려서 errors.Is가 찾지 못한다. %w로 감싸면 체인이 유지되어, 몇 단계를 거쳐 올라온 에러라도 "원인이 문법 오류였나?"를 물을 수 있다 (Go by Example: Errors).

3. defer — 정리는 열자마자 예약한다

Java의 try-with-resources 역할. defer로 등록한 호출은 함수가 리턴하기 직전에 실행되므로, 자원을 연 직후에 닫기를 예약해 두면 어떤 경로로 리턴하든 정리가 보장된다:

func process() {
    fmt.Println("스트림 열기")
    defer fmt.Println("스트림 닫기 (defer)")
    defer fmt.Println("버퍼 비우기 (defer)")
    fmt.Println("처리 중...")
}
스트림 열기
처리 중...
버퍼 비우기 (defer)
스트림 닫기 (defer)

여러 개는 역순(LIFO)으로 실행된다 — 나중에 연 것부터 닫는다. 한 가지 함정: defer의 인자는 defer 문을 만난 시점에 평가된다(치트시트에 검증 예제 있음).

4. 실습 — 해상도 파서

  1. playground/errors를 만들고 go mod init errors-practice 후 main.go 작성: 
    package main

import (
	"errors"
	"fmt"
	"strconv"
	"strings"
)

// parseResolution은 "1920x1080" 형태의 문자열을 파싱해
// 가로, 세로 픽셀 수를 반환한다.
func parseResolution(s string) (int, int, error) {
	parts := strings.Split(s, "x")
	if len(parts) != 2 {
		return 0, 0, fmt.Errorf("해상도 형식이 아님: %q", s)
	}
	w, err := strconv.Atoi(parts[0])
	if err != nil {
		return 0, 0, fmt.Errorf("가로 값 파싱 실패: %w", err)
	}
	h, err := strconv.Atoi(parts[1])
	if err != nil {
		return 0, 0, fmt.Errorf("세로 값 파싱 실패: %w", err)
	}
	return w, h, nil
}

// check는 입력 하나를 파싱해 결과 또는 에러를 출력한다.
func check(in string) {
	w, h, err := parseResolution(in)
	if err != nil {
		fmt.Println("에러:", err)
		if errors.Is(err, strconv.ErrSyntax) {
			fmt.Println("  → 원인: 숫자가 아닌 문자 (strconv.ErrSyntax)")
		}
		return
	}
	fmt.Printf("%s → 가로 %d, 세로 %d\n", in, w, h)
}

func main() {
	check("1920x1080")
	check("1920")
	check("abcxdef")
}
  2. go run .

    예상 출력:

    1920x1080 → 가로 1920, 세로 1080
에러: 해상도 형식이 아님: "1920"
에러: 가로 값 파싱 실패: strconv.Atoi: parsing "abc": invalid syntax
  → 원인: 숫자가 아닌 문자 (strconv.ErrSyntax)

    주목: 마지막 에러 메시지에 우리가 붙인 맥락("가로 값 파싱 실패")과 원인(strconv의 원본 에러)이 콜론으로 이어져 있다 — 이게 래핑 체인의 생김새다.

부숴보기 — 세 가지

  1. check 안을 w, h := parseResolution(in)으로 바꿔(err 빼고) go run .

    예상: assignment mismatch: 2 variables but parseResolution returns 3 values — 에러 반환값을 "몰래 안 받는" 것 자체가 불가능하다. 원상복구.

  2. 이번엔 err는 받되 if err != nil 블록을 통째로 지우고 실행.

    예상: declared and not used: err — 받아놓고 무시하는 것도 컴파일 에러. Java의 삼켜진 예외(swallowed exception)가 Go에선 문법적으로 어렵다. 원상복구.

  3. parseResolution의 %w 두 개를 %v로 바꾸고 실행.

    예상: 에러 메시지는 겉보기에 똑같지만 → 원인: ... 줄이 사라진다 — 래핑 체인이 끊겨 errors.Is가 strconv.ErrSyntax를 못 찾는 것. %w와 %v의 차이가 이 한 줄이다. 원상복구 후 go fmt ./....
