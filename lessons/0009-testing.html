Lesson 0009 · Go 실전

테스트 — 테이블 드리븐이 표준이다

Go의 테스트는 언어에 내장이다 — JUnit 같은 프레임워크도, 어노테이션도 없다. 오늘 배우는 테이블 드리븐 패턴은 Go 커뮤니티의 표준이자 회사 Go 컨벤션이 요구하는 바로 그 형식이다. 예상 소요: 35–40분.

오늘의 목표 (하나만)

segment 패키지에 테이블 드리븐 테스트를 붙이고, -cover가 찾아준 미검증 분기를 케이스 추가로 메워 커버리지 100%를 만든다.

1. go test — 프레임워크가 없는 테스트

규칙은 두 개뿐이다: 파일 이름이 _test.go로 끝나고, 함수가 func TestXxx(t *testing.T) 시그니처면 go test가 알아서 찾아 실행한다. 테스트는 대상 코드와 같은 패키지, 같은 디렉토리에 둔다 (Java의 src/test/java 미러 트리가 없다):

internal/segment/
├── segment.go        // 대상 코드
└── segment_test.go   // 테스트 — 같은 패키지라 비공개 함수도 접근 가능
Java (JUnit)Go
@Test 어노테이션 + 테스트 러너TestXxx(t *testing.T) 시그니처가 전부
assertEquals 등 assertion 라이브러리if got != want { t.Errorf(...) } — 그냥 Go 코드
Maven surefire가 빌드에서 실행go test ./... 명령 하나

2. 테이블 드리븐 + t.Run — 케이스는 데이터다

같은 함수를 입력만 바꿔 여러 번 검증할 때, 테스트 함수를 복붙하는 대신 케이스를 구조체 슬라이스(테이블)로 선언하고 range로 돌린다. 각 케이스를 t.Run(이름, ...) 서브테스트로 감싸면 실패가 케이스 단위로 보고되고, 케이스 하나만 골라 실행할 수도 있다 (Using Subtests and Sub-benchmarks — Go 공식 블로그):

tests := []struct {
    name string
    in   string
    want int
}{
    {name: "정상", in: "6", want: 6},
    {name: "경계", in: "0", want: 0},
}

for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        got := doSomething(tt.in)
        if got != tt.want {
            t.Errorf("got %d, want %d", got, tt.want)
        }
    })
}
  • got/want 관례: 실제 값은 got, 기대값은 want — 실패 메시지도 got X, want Y 순서로. 표준 라이브러리 전체가 이 어휘를 쓴다.
  • t.Errorf vs t.Fatalf: Errorf는 실패를 기록하고 계속 진행, Fatalf는 그 (서브)테스트를 즉시 중단. "이게 틀렸으면 이후 검사가 무의미"할 때만 Fatalf — 예: 에러가 없어야 하는데 있으면, 반환값 비교는 의미가 없다.
  • 새 케이스 추가 = 테이블에 한 줄 — 테스트 로직은 그대로. 이것이 테이블 드리븐의 힘이다.

3. 커버리지 — 안 밟은 분기를 찾아주는 도구

go test ./... -cover                          # 문장 커버리지 % 출력
go test ./internal/segment -coverprofile=cover.out
go tool cover -func=cover.out                 # 함수별 % (터미널)
go tool cover -html=cover.out                 # 안 밟은 줄을 브라우저에서 색으로

숫자 자체보다 "어느 분기를 안 밟았나"가 진짜 정보다 — 실습에서 직접 겪는다.

4. 실습 — segment 패키지에 테스트 붙이기

  1. 레슨 0008의 playground/mediakit에서 이어간다. 0008 실습을 건너뛰었다면: playground/mediakit을 만들고 go mod init mediakit 후, internal/segment/segment.go에 아래 내용(레슨 0002·0003의 함수를 패키지로 옮긴 것)을 저장: 
    // Package segment는 스트림 세그먼트 계산과 해상도 파싱을 담당한다.
package segment

import (
	"fmt"
	"strconv"
	"strings"
)

// ParseResolution은 "1920x1080" 형태의 문자열을 파싱해
// 가로, 세로 픽셀 수를 반환한다.
func ParseResolution(s string) (int, int, error) {
	parts := strings.Split(s, "x")
	if len(parts) != 2 {
		return 0, 0, fmt.Errorf("해상도 형식이 아님: %q", s)
	}
	w, err := strconv.Atoi(parts[0])
	if err != nil {
		return 0, 0, fmt.Errorf("가로 값 파싱 실패: %w", err)
	}
	h, err := strconv.Atoi(parts[1])
	if err != nil {
		return 0, 0, fmt.Errorf("세로 값 파싱 실패: %w", err)
	}
	return w, h, nil
}

// SplitSegments는 총 재생 시간(초)을 세그먼트 길이로 나눠
// 온전한 세그먼트 개수와 남는 초를 반환한다.
func SplitSegments(totalSec, segLen int) (int, int) {
	return totalSec / segLen, totalSec % segLen
}
  2. 같은 디렉토리에 segment_test.go 작성 — 에러 케이스는 errors.Is로 원인까지 검증한다: 
    package segment

import (
	"errors"
	"strconv"
	"testing"
)

// TestParseResolution은 정상·에러 입력을 테이블로 검증한다.
func TestParseResolution(t *testing.T) {
	tests := []struct {
		name   string
		in     string
		wantW  int
		wantH  int
		wantOK bool  // 성공을 기대하는가
		wantIs error // 기대하는 원인 에러 (nil이면 검사 생략)
	}{
		{name: "FHD", in: "1920x1080", wantW: 1920, wantH: 1080, wantOK: true},
		{name: "UHD_4K", in: "3840x2160", wantW: 3840, wantH: 2160, wantOK: true},
		{name: "구분자_없음", in: "1920", wantOK: false},
		{name: "숫자_아님", in: "abcxdef", wantOK: false, wantIs: strconv.ErrSyntax},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			w, h, err := ParseResolution(tt.in)

			if tt.wantOK {
				if err != nil {
					t.Fatalf("에러가 없어야 하는데: %v", err)
				}
				if w != tt.wantW || h != tt.wantH {
					t.Errorf("got %dx%d, want %dx%d", w, h, tt.wantW, tt.wantH)
				}
				return
			}

			if err == nil {
				t.Fatal("에러를 기대했지만 nil")
			}
			if tt.wantIs != nil && !errors.Is(err, tt.wantIs) {
				t.Errorf("원인 에러 불일치: got %v, want %v", err, tt.wantIs)
			}
		})
	}
}

// TestSplitSegments는 세그먼트 분할 계산을 테이블로 검증한다.
func TestSplitSegments(t *testing.T) {
	tests := []struct {
		name              string
		totalSec, segLen  int
		wantFull, wantRem int
	}{
		{name: "나머지_있음", totalSec: 95, segLen: 6, wantFull: 15, wantRem: 5},
		{name: "딱_떨어짐", totalSec: 60, segLen: 6, wantFull: 10, wantRem: 0},
		{name: "세그먼트보다_짧음", totalSec: 4, segLen: 6, wantFull: 0, wantRem: 4},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			full, rem := SplitSegments(tt.totalSec, tt.segLen)
			if full != tt.wantFull || rem != tt.wantRem {
				t.Errorf("got (%d, %d), want (%d, %d)", full, rem, tt.wantFull, tt.wantRem)
			}
		})
	}
}

  4. 이제 커버리지: go test ./... -cover

    예상: coverage: 90.9% of statements — 다 통과했는데 100%가 아니다. 범인을 찾자:

    go test ./internal/segment -coverprofile=cover.out
go tool cover -func=cover.out
    mediakit/internal/segment/segment.go:12:	ParseResolution	90.0%
mediakit/internal/segment/segment.go:30:	SplitSegments	100.0%
total:						(statements)	90.9%

    ParseResolution의 어느 분기가 안 밟혔을까? "abcxdef"는 가로 파싱에서 이미 실패하므로, "세로 값 파싱 실패" 분기는 아무 케이스도 안 밟는다. 커버리지가 테스트 설계의 구멍을 찾아준 것.

  5. 테이블에 한 줄 추가 — 이게 테이블 드리븐의 힘이다: 
    {name: "세로가_숫자_아님", in: "1080xabc", wantOK: false, wantIs: strconv.ErrSyntax},

    다시 go test ./... -cover → coverage: 100.0% of statements. 테스트 로직은 한 글자도 안 바꿨다.

부숴보기 — 실패를 읽는 법

  1. 나머지_있음 케이스의 wantFull: 15를 16으로 일부러 틀리게 하고 go test ./...

    예상:

    --- FAIL: TestSplitSegments (0.00s)
    --- FAIL: TestSplitSegments/나머지_있음 (0.00s)
        segment_test.go:66: got (15, 5), want (16, 5)
FAIL
FAIL	mediakit/internal/segment	0.433s

    읽는 순서: 어느 테스트의 어느 케이스가(/나머지_있음), 어느 파일 몇 번째 줄에서(segment_test.go:66), 실제로 뭘 받았고 뭘 기대했나(got/want). 다른 케이스는 계속 실행됐다는 점도 확인(Errorf라서). 원상복구.

  2. 서브테스트 하나만 실행: go test ./internal/segment -run 'TestParseResolution/숫자_아님' -v

    예상: 해당 케이스만 RUN/PASS — 큰 테이블에서 실패한 케이스 하나만 반복 실행할 때의 무기다. 참고로 코드 변경 없이 재실행하면 ok ... (cached)가 붙는다 — 캐시를 무시하려면 -count=1.
