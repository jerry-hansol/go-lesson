Lesson 0020 · Pion·WebRTC

실전의 pion — mediamtx·LiveKit 해부

Pion·WebRTC 아크의 피날레. 0015~0019에서 배운 프로토콜 지식을 들고, pion을 가장 크게 쓰는 두 실코드를 연다. 이 투어는 mediamtx 커밋 9934156(2026-08-19, 레슨 0014와 동일)과 livekit 커밋 6a64df2(2026-08-20) 기준 — 구조는 바뀔 수 있다. 예상 소요: 60분.

오늘의 목표 (하나만)

pion 생태계의 모듈 지도를 그리고, mediamtx의 WHIP 처리와 LiveKit SFU에서 pion이 쓰이는 지점을 실제 파일:줄로 짚을 수 있다 — 회사 pion 코드베이스를 열 준비 완료.

1. pion 생태계 지도 — webrtc는 파사드일 뿐

pion/webrtc는 상위 파사드고, 프로토콜 계층마다 독립 Go 모듈이 있다. pion org에서 실측한 주요 모듈(2026-08-20 기준):

모듈담당배운 레슨

이 구조가 실코드에서 어떻게 보이나 — mediamtx go.mod 실물: 직접 의존이 webrtc/v4 v4.2.18, ice/v4, interceptor, rtp, rtcp, sdp/v3이고, dtls/v3·srtp/v3·sctp·stun/v3·turn/v5는 // indirect로 딸려 온다. 파사드만 부르면 프로토콜 가족 전체가 조립되는 것이다.

2. interceptor — RTP/RTCP의 미들웨어 체인

pion/interceptor는 "Pluggable RTP/RTCP processors" — HTTP 미들웨어처럼 패킷 경로에 끼어드는 체인이다. NACK 재전송, 수신 리포트 생성 같은 RTCP 자동화가 전부 interceptor로 구현되어 PeerConnection에 꽂힌다.

mediamtx는 커스텀 interceptor를 직접 만든다. internal/protocols/webrtc/stats_interceptor.go:19:

func (s *statsInterceptor) BindRTCPReader(reader interceptor.RTCPReader) interceptor.RTCPReader {
	return interceptor.RTCPReaderFunc(func(bytes []byte,
		attributes interceptor.Attributes,
	) (int, interceptor.Attributes, error) {

낯익지 않은가 — 레슨 0006의 암묵적 인터페이스 구현과 http.HandlerFunc(0010) 스타일의 함수 어댑터가 그대로다. 등록은 peer_connection.go:324의 interceptorRegistry := &interceptor.Registry{}에 꽂는 방식이다.

3. mediamtx 속 pion — WHIP: 시그널링 공백을 HTTP로 메운 표준

0015에서 배웠듯 WebRTC 표준은 시그널링 방법을 정하지 않는다. 그 공백을 스트리밍 서비스용으로 메운 것이 WHIP(WebRTC-HTTP Ingestion Protocol, RFC 9725, 2025) — offer를 HTTP POST 바디로 보내고 answer를 응답으로 받는, 사실상 "시그널링의 REST화"다. WHEP은 같은 모델의 재생(egress) 방향이다.

mediamtx의 구현 실물 — internal/servers/webrtc/http_server.go:

// :39 — 라우팅은 정규식으로
reWHIPWHEPNoID = regexp.MustCompile("^/(.+?)/(whip|whep)$")

// :194 — offer가 HTTP POST 바디로 들어온다
func (s *httpServer) onWHIPPost(ctx *gin.Context, pathName string, publish bool) {
	contentType := httpp.ParseContentType(ctx.Request.Header.Get("Content-Type"))
	if contentType != "application/sdp" { ... }
	offer, err := io.ReadAll(&customLimitReader{ctx.Request.Body, maxInboundSDPSize})

offer는 세션으로 넘어가 internal/protocols/webrtc/peer_connection.go:725에서 0015의 3박자가 그대로 나온다:

err := co.wr.SetRemoteDescription(*offer)   // :725
tmp, err := co.wr.CreateAnswer(nil)          // :730
err = co.wr.SetLocalDescription(*answer)     // :739

재미있는 디테일: http_server.go:386 주석은 아직 RFC draft-ietf-whip-09를 가리킨다 — RFC 9725로 승격되기 전 초안 번호다. 0014 플레이북의 교훈 그대로, 코드 주석은 낡는다.

4. LiveKit 속 pion — replace로 포크를 태우는 SFU

livekit go.mod에는 pion 스위트가 직접 의존으로 있고, 그 아래 이런 줄이 있다 (go.mod:166~170 실물):

replace github.com/pion/webrtc/v4 => github.com/livekit/webrtc-pion/v4 v4.2.18-warp.1
replace github.com/pion/dtls/v3   => github.com/livekit/dtls/v3        v3.1.5-warp.1
replace github.com/pion/ice/v4    => github.com/livekit/ice/v4         v4.4.0-warp.1

replace는 go.mod 심화 문법(0008의 연장)으로, "이 모듈을 부르면 실제로는 저걸 써라"는 치환 지시다. LiveKit은 pion 코어 3종을 -warp.N 버전의 자체 포크로 바꿔 태운다. 이유를 밝힌 문서는 포크 리포에 없지만, 커밋 이력에는 자체 기능 패치(예: multi-track ogg writing API 추가)가 올라가 있다 — upstream 반영을 기다리지 않고 패치를 선탑재하는 구조로 읽힌다.

SFU 코어에서 0019의 포워딩이 어떤 모습인지 — pkg/sfu/downtrack.go:249 주석 실물:

// DownTrack implements webrtc.TrackLocal, is the track used to write packets
// to SFU Subscriber, the track handle the packets for simple, simulcast
// and SVC Publisher.

구독자에게 나가는 트랙이 pion의 webrtc.TrackLocal 인터페이스를 암묵 구현한 커스텀 타입이다 (Bind :447, WriteRTP :1025). 0006에서 배운 그 메커니즘이 SFU의 심장이고, 레이어 선택은 pkg/sfu/forwarder.go:353의 Forwarder.DetermineCodec(codec webrtc.RTPCodecCapability, ...) 같은 지점에서 pion 타입을 직접 받는다.

시작점: internal/servers/webrtc/http_server.go:194의 onWHIPPost → newSessionReq. 이어서 grep -n "PeerConnection{" internal/servers/webrtc/session.go.
