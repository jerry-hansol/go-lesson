Lesson 0007 · Go 기초

고루틴과 채널 — 미디어 서버가 Go를 쓰는 이유

기초 아크의 피날레. MediaMTX가 스트림 수백 개를, LiveKit이 참가자 수천 명을 한 프로세스에서 받아내는 메커니즘이 오늘 주제다. 예상 소요: 40분.

오늘의 목표 (하나만)

세그먼트 6개를 병렬 트랜스코딩하는 프로그램을 작성해 3초 → 0.5초 단축을 직접 측정하고, 데드락 에러 전문을 읽고 원인을 설명할 수 있다.

1. 고루틴 — 스레드가 아니라 훨씬 싼 것

함수 호출 앞에 go 한 단어를 붙이면 동시 실행이다 (Go by Example: Goroutines):

go transcode(seg)     // 새 고루틴에서 실행 — 기다리지 않고 다음 줄로
Java 스레드고루틴
초기 스택~1MB (OS 스레드)수 KB — 필요하면 자람
현실적 개수수천 개면 부담수십만 개도 일상
생성 문법ExecutorService 등 라이브러리언어 키워드 go

미디어 서버의 현실이 바로 이 표다: 연결 하나당 읽기·쓰기·타임아웃용 고루틴을 여러 개 띄우는 설계가 Go에서는 기본형이다.

규칙 하나: main 함수가 리턴하면 실행 중이던 고루틴은 그 즉시 전부 죽는다. 기다려주지 않는다 — 그래서 다음이 필요하다.

2. sync.WaitGroup — 다 끝날 때까지 기다리기

Java의 CountDownLatch에 해당한다 (Go by Example: WaitGroups):

var wg sync.WaitGroup
for id := 1; id <= 6; id++ {
    wg.Add(1)                  // 카운터 +1 (go 띄우기 전에!)
    go func() {
        defer wg.Done()        // 레슨 0003의 defer — 끝나면 반드시 -1
        transcode(id)
    }()
}
wg.Wait()                      // 카운터가 0이 될 때까지 블록

참고: 클로저가 루프 변수 id를 잡는 건 Go 1.22부터 반복마다 새 변수라 안전하다. 그 이전 코드베이스(여러분이 읽을 미디어 서버 코드 포함)에서는 go func(id int) {...}(id)처럼 인자로 넘기는 패턴을 보게 될 것이다.

3. 채널 — 고루틴 사이의 파이프

Go 동시성의 슬로건: "메모리를 공유해서 통신하지 말고, 통신해서 메모리를 공유하라" (Effective Go — Share by communicating). 그 통신 수단이 채널이다 (Go by Example: Channels):

results := make(chan string)   // string이 흐르는 unbuffered 채널
results <- "seg-1.ts 완료"      // 송신 (채널이 왼쪽)
r := <-results                 // 수신 (채널이 오른쪽)
  • unbuffered 채널은 동기화 지점이다: 송신은 수신자가 받아갈 때까지, 수신은 송신자가 보낼 때까지 블록된다. 락 없이 "전달 완료"가 보장되는 이유.
  • 버퍼가 필요하면 make(chan string, 100) — Java의 BlockingQueue에 가깝지만 언어 내장이다 (Channel Buffering).

4. close와 range — "더 안 온다"를 알리는 법

close(results)                 // 생산자가 닫는다 (수신자는 닫지 않는다)
for r := range results {       // 채널이 닫혀 비워질 때까지 수신
    fmt.Println(r)
}

range 루프는 채널이 close되어야 끝난다 (Range over Channels, Closing Channels). 안 닫으면? 부숴보기에서 직접 본다. (여러 채널을 동시에 기다리는 select는 다음 심화 레슨에서.)

5. 실습 — 세그먼트 병렬 트랜스코딩

  1. playground/concurrency를 만들고 (go mod init concurrency) 먼저 순차 버전을 작성: 
    package main

import (
	"fmt"
	"time"
)

// transcode는 세그먼트 하나를 트랜스코딩하는 척한다 (0.5초짜리 작업).
func transcode(id int) string {
	time.Sleep(500 * time.Millisecond)
	return fmt.Sprintf("seg-%d.ts 완료", id)
}

func main() {
	start := time.Now()
	for id := 1; id <= 6; id++ {
		fmt.Println(transcode(id))
	}
	fmt.Println("총 소요:", time.Since(start).Round(10*time.Millisecond))
}

    예상: seg-1부터 순서대로 출력되고 총 소요: 3.01s — 6 × 0.5초.

  2. 이제 main을 병렬 버전으로 교체: 
    func main() {
	start := time.Now()

	results := make(chan string)
	var wg sync.WaitGroup

	for id := 1; id <= 6; id++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			results <- transcode(id)
		}()
	}

	// 워커가 전부 끝나면 채널을 닫는다 — 닫혀야 아래 range가 끝난다
	go func() {
		wg.Wait()
		close(results)
	}()

	for r := range results {
		fmt.Println(r)
	}
	fmt.Println("총 소요:", time.Since(start).Round(10*time.Millisecond))
}

    import에 "sync" 추가. 예상: 순서는 뒤섞여 나오고(고루틴 완료 순서는 비결정적 — 실행마다 다르다) 총 소요: 500ms. 방금 6배를 벌었다.

부숴보기 — 동시성 사고 3종

  1. 병렬 버전에서 WaitGroup·채널을 다 빼고 go func() { fmt.Println(transcode(id)) }()만 남긴 뒤 실행.

    예상: 아무것도 출력되지 않고 정상 종료된다. 에러조차 없다 — main이 고루틴을 기다리지 않고 리턴했기 때문. 동시성 버그가 무서운 이유(조용함)를 기억할 것.

  2. 새 파일에서 아무도 수신하지 않는 채널에 송신해 보기: ch := make(chan string); ch <- "hello"

    예상 출력 (전문을 읽어보자):

    fatal error: all goroutines are asleep - deadlock!

goroutine 1 [chan send]:
main.main()
	.../main.go:5 +0x34
exit status 2

    [chan send]가 "송신에서 멈춰 있다"는 뜻이다. 런타임이 전원 잠든 것을 감지해 즉사시켜 준다 — 침묵보다 훨씬 나은 실패.

  3. 닫힌 채널에 송신: ch := make(chan int, 1); close(ch); ch <- 1

    예상: panic: send on closed channel. 그래서 규칙이 "닫는 건 생산자, 그것도 한 번만"이다.
