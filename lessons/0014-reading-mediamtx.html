Lesson 0014 · Go 실전 · 코드 리딩

실코드 읽기 — mediamtx 투어

미션의 도착점이다: "미디어 서버 프로젝트를 열어 구조를 파악할 수 있다." 오늘 진짜 프로덕션 미디어 서버(bluenviron/mediamtx)를 클론해서 그걸 한다. 예상 소요: 60분.

오늘의 목표 (하나만)

mediamtx에서 진입점 → 디렉토리 지도 → 핵심 인터페이스 → RTMP publish 경로의 입구까지, 코드 리딩 플레이북 5단계를 스스로 실행한다.

1. 방법론 — 다 읽으려 하지 않는다

낯선 코드베이스는 정독의 대상이 아니라 지도 그리기의 대상이다. 절차는 다섯 단계 — 상세는 플레이북에 있고, 오늘은 이걸 실전에 적용한다:

① 진입점(0001) → ② 디렉토리 지도(0008) → ③ 인터페이스가 경계(0006) → ④ 데이터의 여정 하나(0007) → ⑤ 테스트가 사용 설명서(0009)

2. 투어 준비

  1. 클론: 
    cd ~/Desktop/repo/learn-go/playground
git clone --depth 1 https://github.com/bluenviron/mediamtx
cd mediamtx

    이 투어는 2026-08-19의 main 브랜치 (커밋 9934156, v1.20.1 직후) 기준이다. 구조는 바뀔 수 있다 — 다르면 그게 바로 grep 연습 기회다.

  2. 신원 확인: head -3 go.mod

    예상: 모듈 github.com/bluenviron/mediamtx, go 1.26.0 — 여러분 로컬과 같은 Go 버전이다.

3. ① 진입점 — main.go 전문 (15줄이 전부다)

// main executable.
package main

import (
	"os"

	"github.com/bluenviron/mediamtx/internal/core"
)

func main() {
	s, ok := core.New(os.Args[1:])
	if !ok {
		os.Exit(1)
	}
	s.Wait()
}

프로덕션 미디어 서버의 main이 이게 전부다. 배운 게 다 보인다 — ok 불리언 반환(레슨 0002), 조립은 internal/core에 위임. 그리고 s.Wait()의 실제 구현(internal/core/core.go:299)은:

func (p *Core) Wait() {
	<-p.done
}

레슨 0007의 채널 수신 한 줄이 서버 전체의 수명을 지탱한다. main 고루틴은 여기 블록되고, 종료 신호가 done 채널로 올 때까지 모든 일은 다른 고루틴들이 한다.

4. ② 디렉토리 지도

mediamtx/
├── main.go            ← 방금 봤다
├── go.mod / go.sum
├── mediamtx.yml       ← 기본 설정 파일
├── api/               ← OpenAPI 명세
├── docs/              ← 문서
└── internal/          ← 본체 전부 (외부 import 금지 구역)
    ├── core/          ← 조립실: Core struct가 모든 서버를 초기화·소유
    ├── servers/       ← 프로토콜별 서버: rtmp, rtsp, hls, webrtc, srt, moq
    ├── stream/        ← 스트림 데이터 경로 (미디어가 흐르는 곳)
    ├── defs/          ← 공유 인터페이스·타입 정의 (Publisher, Reader, Path...)
    ├── conf/          ← 설정 파싱·검증
    ├── auth/          ← 인증
    ├── logger/        ← 로깅
    ├── protocols/     ← 프로토콜 유틸
    ├── staticsources/ ← 카메라 등 고정 소스 pull
    ├── recorder/ + playback/ ← 녹화와 재생
    └── ...            ← metrics, pprof, externalcmd 등

ls internal/servers/를 직접 실행해 보라 — 프로토콜 하나가 패키지 하나, 회사에서 다루는 SRT·WebRTC가 각각 어디 사는지 바로 보인다.

5. ③ 인터페이스가 경계다

grep -rn "interface {" internal/defs/를 실행하면 이 서버의 등장인물 목록이 나온다. 그중 internal/defs/publisher.go 전문:

package defs

// Publisher is an entity that can publish a stream.
type Publisher interface {
	Source
	Close()
}

레슨 0006에서 여러분이 만든 것과 같은 이름의 인터페이스가 실물로 있다. 새 문법 하나: 인터페이스 안에 Source처럼 다른 인터페이스 이름을 쓰면 그 메서드 셋을 통째로 포함한다(인터페이스 임베딩 — Java의 인터페이스 extends에 대응).

더 중요한 발견은 internal/servers/rtmp/server.go:65다:

type serverPathManager interface {
	FindPathConf(req defs.PathFindPathConfReq) (*defs.PathFindPathConfRes, error)
	AddPublisher(req defs.PathAddPublisherReq) (*defs.PathAddPublisherRes, error)
	AddReader(req defs.PathAddReaderReq) (*defs.PathAddReaderRes, error)
}

RTMP 서버가 "내가 pathManager에게 필요한 건 이 세 개뿐"이라고 사용하는 쪽에서 소문자(비공개) 인터페이스로 선언했다 — 0006에서 배운 "인터페이스는 사용하는 쪽이 정의한다" 철학이 프로덕션에서 실제로 이렇게 쓰인다. 덕분에 이 패키지는 pathManager의 실물 없이 테스트할 수 있다.

7. 추적 과제 — RTMP publish의 여정 (답은 직접)

OBS가 RTMP로 송출을 시작하면 그 연결은 어떤 경로로 스트림이 되는가? 힌트만 준다:

  1. 시작점: internal/servers/rtmp/listener.go — 연결을 받으면 무엇을 go로 띄우는지 보라.
  2. grep -n "runPublish" internal/servers/rtmp/conn.go — 분기 지점(publish냐 read냐)을 찾아라.
  3. grep -rn "AddPublisher" internal/servers/rtmp/ — 이 연결이 pathManager에 도착하는 줄을 찾으면 성공. 거기서 Author: c가 무슨 뜻인지 5장의 인터페이스와 연결해 보라.
  4. 여력이 있으면 ⑤단계도: internal/servers/rtmp/server_test.go를 열어 테스트가 서버를 어떻게 띄우고 publish를 흉내 내는지 훑어보라.
