Lesson 0017 · Pion·WebRTC

DataChannel과 보안 계층 — DTLS 위의 제3의 전송

미디어를 다루기 전에 그 아래 깔리는 두 층을 먼저 연다: 모든 것을 암호화하는 DTLS, 그리고 TCP도 UDP도 아닌 SCTP 위의 DataChannel. 예상 소요: 40–45분.

오늘의 목표 (하나만)

내 맥에서 DTLS로 암호화된 DataChannel을 열어 ping-pong RTT를 실측하고, 신뢰성 옵션(순서 X·재전송 0회)이 SDP 협상으로 실제 반영되는 것을 두 눈으로 확인한다.

1. 보안은 선택이 아니다 — DTLS와 지문

WebRTC에는 "암호화 없는 모드"가 없다. ICE(0016)가 경로를 찾으면 그 위에서 곧바로 DTLS 핸드셰이크(TLS의 UDP판)가 일어나고, 이후의 모든 것 — 데이터도 미디어도 — 이 그 열쇠로 잠긴다 (WebRTC for the Curious — Securing):

┌───────────────┬────────────────┐
│  DataChannel  │  미디어(Track)  │  ← 애플리케이션이 만지는 층 (Track은 0018)
├───────────────┼────────────────┤
│     SCTP      │      SRTP      │  ← 데이터 전송        미디어 암호화
├───────────────┴────────────────┤
│     DTLS  (암호화·키 합의)       │  ← 오늘의 주인공
├────────────────────────────────┤
│     ICE   (경로 찾기 — 0016)    │
└────────────────────────────────┘
              UDP

재미있는 건 신뢰의 출처다. 인증서는 보통 자가서명이라 CA가 없다. 대신 인증서의 해시(지문)를 SDP의 a=fingerprint 라인에 실어 시그널링으로 미리 보내고, DTLS 핸드셰이크에서 받은 실제 인증서와 대조한다. 즉 시그널링 채널(실무에선 HTTPS/WSS)이 신뢰의 뿌리다 — 시그널링이 뚫리면 중간자도 가능하다. 미디어는 DTLS에서 유도한 키로 SRTP가 암호화한다 (상세는 0018).

2. DataChannel = SCTP over DTLS

임의의 바이트를 P2P로 보내는 DataChannel은 TCP(신뢰·순서 보장이지만 하나 막히면 전부 대기)도 UDP(아무 보장 없음)도 아닌 제3의 선택 — SCTP를 DTLS 위에 태운 것이다 (Data Communication). SCTP를 고른 이유는 두 가지다: 한 연결에 독립적인 스트림 여러 개(채널 하나가 막혀도 다른 채널은 진행), 그리고 스트림마다 신뢰성을 골라 설정할 수 있다는 것.

이 계층 구조는 pion에서 상상이 아니라 모듈 목록 그 자체다. go get github.com/pion/webrtc/v4 하나로 끌려온 의존성이 프로토콜 스택을 그대로 비춘다:

3. 신뢰성 옵션 — 데이터 성격이 설정을 정한다

채널을 만들 때 webrtc.DataChannelInit으로 정한다 (신뢰성 옵션):

옵션의미기본값
Ordered순서 보장 여부true
MaxRetransmits재전송 횟수 상한nil = 무제한 재전송
(둘은 상호 배타 — 하나만 지정)
MaxPacketLifeTime재전송 유효 시간(ms)
보내는 것맞는 설정왜
채팅, 파일 조각, 제어 명령기본값 (순서·신뢰)하나라도 빠지면 안 됨
게임 좌표, 실시간 상태값Ordered:false, MaxRetransmits:0늦은 옛 값은 쓰레기 — 최신만 중요
라이브 자막·텔레메트리Ordered:false, MaxPacketLifeTime:nn ms 안에 못 가면 포기

미디어 서버 실무에서 미디어 자체는 SRTP로 가지만, 참가자 메타데이터·컨트롤 메시지·통계 같은 부가 데이터가 DataChannel로 다닌다 — LiveKit이 대표적이다 (0020에서 실코드로 확인).

4. 실습 — 암호화된 ping-pong과 옵션 협상

  1. playground/webrtc-datachannel 디렉토리에서 모듈 초기화 후 pion을 가져온다: 
    go mod init webrtcdc
go get github.com/pion/webrtc/v4

    첫 외부 의존성이다! go.mod에 require github.com/pion/webrtc/v4 v4.2.x가 생기고 §2의 스택이 통째로 딸려온다.

  2. main.go 작성 — 레슨 0015의 "한 프로세스 두 피어" 패턴에 채널 두 개를 얹는다: 
    package main

import (
	"fmt"
	"strings"
	"time"

	"github.com/pion/webrtc/v4"
)

// must는 실습 편의를 위한 헬퍼 — 에러 시 즉시 중단한다.
func must(err error) {
	if err != nil {
		panic(err)
	}
}

// fmtRetransmits는 *uint16 옵션 값을 출력용 문자열로 바꾼다 (nil = 제한 없음).
func fmtRetransmits(p *uint16) string {
	if p == nil {
		return "제한없음"
	}
	return fmt.Sprintf("%d회", *p)
}

func main() {
	// 1. 같은 프로세스에 피어 두 개 — 시그널링 서버 없이 SDP를 변수로 직접 전달한다.
	pc1, err := webrtc.NewPeerConnection(webrtc.Configuration{})
	must(err)
	pc2, err := webrtc.NewPeerConnection(webrtc.Configuration{})
	must(err)
	defer pc1.Close()
	defer pc2.Close()

	done := make(chan struct{})

	// 2. pc1: 기본 채널(신뢰·순서 보장)과 unreliable 채널(순서 X, 재전송 0회)을 만든다.
	ping, err := pc1.CreateDataChannel("ping", nil)
	must(err)

	unordered := false
	var zeroRetx uint16 = 0
	_, err = pc1.CreateDataChannel("state", &webrtc.DataChannelInit{
		Ordered:        &unordered, // false = 순서 보장 안 함
		MaxRetransmits: &zeroRetx,  // 0 = 재전송 안 함 (최신 값만 중요할 때)
	})
	must(err)

	// 3. pc2: 상대가 연 채널을 받는다. 협상된 신뢰성 옵션을 그대로 읽을 수 있다.
	pc2.OnDataChannel(func(dc *webrtc.DataChannel) {
		fmt.Printf("[pc2] 채널 수신: %-5s (ordered=%v, maxRetransmits=%s)\n",
			dc.Label(), dc.Ordered(), fmtRetransmits(dc.MaxRetransmits()))
		if dc.Label() == "ping" {
			dc.OnMessage(func(msg webrtc.DataChannelMessage) {
				// ping이 오면 pong으로 되돌려준다.
				must(dc.SendText(strings.Replace(string(msg.Data), "ping", "pong", 1)))
			})
		}
	})

	// 4. pc1: ping 채널이 열리면 왕복 5회 RTT를 측정한다.
	var sentAt time.Time
	round := 1
	ping.OnMessage(func(msg webrtc.DataChannelMessage) {
		fmt.Printf("[pc1] %s 수신 (RTT %v)\n", string(msg.Data), time.Since(sentAt).Round(10*time.Microsecond))
		if round == 5 {
			close(done)
			return
		}
		round++
		sentAt = time.Now()
		must(ping.SendText(fmt.Sprintf("ping %d", round)))
	})
	ping.OnOpen(func() {
		fmt.Println("[pc1] ping 채널 열림 — 왕복 5회 시작")
		sentAt = time.Now()
		must(ping.SendText("ping 1"))
	})

	// 5. 시그널링: offer/answer를 변수로 교환한다 (trickle 대신 gathering 완료 후 한 방에).
	offer, err := pc1.CreateOffer(nil)
	must(err)
	must(pc1.SetLocalDescription(offer))
	<-webrtc.GatheringCompletePromise(pc1)

	// DTLS 인증서 지문이 SDP에 실려 가는 것을 실물로 확인한다.
	for _, line := range strings.Split(pc1.LocalDescription().SDP, "\r\n") {
		if strings.HasPrefix(line, "a=fingerprint") {
			fmt.Printf("[pc1 SDP] %.60s...\n", line)
		}
	}

	must(pc2.SetRemoteDescription(*pc1.LocalDescription()))
	answer, err := pc2.CreateAnswer(nil)
	must(err)
	must(pc2.SetLocalDescription(answer))
	<-webrtc.GatheringCompletePromise(pc2)
	must(pc1.SetRemoteDescription(*pc2.LocalDescription()))

	<-done
	fmt.Println("완료 — DTLS 위에서 암호화된 채널로 5회 왕복")
}
  3. go vet ./... && go run .

[pc1] ping 채널 열림 — 왕복 5회 시작
[pc1] pong 1 수신 (RTT 120µs)
[pc1] pong 2 수신 (RTT 240µs)
[pc1] pong 3 수신 (RTT 70µs)
[pc1] pong 4 수신 (RTT 170µs)

    읽을 것 세 가지: ① a=fingerprint — DTLS 인증서 지문이 SDP에 실려 가는 실물 (인증서는 PeerConnection마다 새로 생성되니 지문 값은 실행마다 다르다). ② state 채널의 ordered=false, maxRetransmits=0회 — pc1이 지정한 옵션이 협상을 거쳐 pc2에서 그대로 읽힌다. ③ RTT 수십~수백 µs — 네트워크가 없는 루프백이라 이 값은 순수하게 DTLS+SCTP 스택 통과 비용이다.

부숴보기 — 콜백의 함정 두 가지

  1. OnMessage를 늦게 등록하면? pc2 쪽 dc.OnMessage(...) 등록을 go func(){ time.Sleep(300*time.Millisecond); ... }()로 감싸 300ms 늦추고, pc1은 열리자마자 ping 1, 500ms 뒤 ping 2를 보내게 바꿔 실행: 
    [pc1] 열림 즉시 ping 1 전송
[pc2] (300ms 뒤에야 OnMessage 등록)
[pc1] 500ms 뒤 ping 2 전송
[pc2] 수신: ping 2
종료 — 수신 로그에 뭐가 찍혔는지 보라

    ping 1은 어디에도 없다 — 에러도 없이 조용히 유실됐다. pion은 핸들러 등록 전에 도착한 메시지를 버퍼링하지 않는다. 그래서 관례는 "OnDataChannel 콜백 안에서 즉시 OnMessage부터 등록"이다. 확인 후 원상복구.

  2. 닫힌 채널에 Send하면? 왕복이 끝난 뒤 ping.Close() 하고 SendText를 한 번 더: 
    Send 에러: io: read/write on closed pipe (상태: closed)

    panic이 아니라 error 반환이다 — 레슨 0003의 (값, error) 관례가 여기서도. Go 채널의 "닫힌 채널 송신 = panic"(0007)과 대비되는 지점이니 헷갈리지 말 것.
